「Pythonでポイ活を完全自動化すれば、寝ている間にもポイントが増えるのではないか」

技術的には、ブラウザを自動操作してボタンを押したり、ページを巡回したりすることは可能です。しかし、ゲームの自動周回、広告の自動閲覧、CAPTCHAの回避などは、サービス規約や案件条件に反する可能性があります。

実際、ポイントインカムの「脳トレクイズ」では、ボット、マクロ、チートツールなどによる不正操作を禁止し、違反時にはサービス利用停止やクイズスタンプ没収などの措置を取ると明記しています。[ポイントインカム「脳トレクイズ」遊び方](https://pointi.kantangame.com/quiz/howto)

モッピーも、複数アカウント、なりすまし、他人のアカウント利用、サービスが想定していない手段でのポイント獲得などを不正行為として挙げ、アカウントの制限・削除やポイント取消の対象になると説明しています。[モッピー「不正行為への取り組み」](https://pc.moppy.jp/st/info/anti_fraud/)

つまり、ポイント獲得操作を無理に自動化すると、積み上げたポイントやアカウントを失う危険があります。

そこで本記事では、クリックBotではなく、次の作業をPythonで自動化します。

- ポイント案件の収集と比較
- 獲得条件・対象外条件の記録
- 利用日・注文情報・証拠の保存
- 判定中・承認・否認・付与済みの追跡
- ポイント付与漏れと失効期限の検知
- 規約変更や取得エラーの通知
- KPIによる採算性と保守コストの評価

結論からいうと、ポイ活で無人化しやすいのは「ポイントを獲得する操作」ではなく、**調査・記録・照合・通知という管理作業**です。

> 本記事は一般的な情報提供を目的としています。ポイント獲得や収益を保証するものではありません。利用前に各サービスの最新規約、案件条件、税務上の扱いを公式情報や専門家へ確認してください。

## ポイ活のWeb自動化はどこまで可能か

Web自動化とは、ブラウザやAPI、CSV、メールなどから情報を取得し、判定・保存・通知までをプログラムに任せる仕組みです。

ポイ活では、作業を次の3段階に分けると、危険な自動化を避けやすくなります。

| 自動化レベル | 機械に任せる作業 | 人間が行う作業 |
|---|---|---|
| レベル1：可視化 | 案件整理、期限管理、還元率比較 | 利用する案件の選択 |
| レベル2：半自動 | 証拠保存、付与照合、異常通知 | 購入、申込み、回答、本人確認 |
| レベル3：許可済み自動処理 | 公式APIなど、明示的に認められた処理 | 異常時の確認 |

自動化候補として比較的扱いやすいのは、次の作業です。

- 公式CSVの読み込み
- 利用明細メールの整理
- 手動で保存した案件情報の集計
- 付与予定日と現在日の比較
- ポイント失効前の通知
- 重複案件の検知
- 実行ログとKPIの作成

一方、次の操作は自動化対象から外します。

- 広告の自動クリックや自動閲覧
- ゲームやアンケートの代理実行
- CAPTCHAやアクセス制限の回避
- 複数アカウントの作成・操作
- ブラウザ指紋やアクセス元の偽装
- 虚偽情報を使った申込み
- 本人確認の代行
- 規約や案件条件を確認できない処理

「規約にBot禁止と書かれていない」という理由だけで許可済みとは判断できません。包括的な不正利用禁止条項や、広告主側の成果条件に抵触する場合があるためです。

## 消費者庁の資料から分かる確認項目

消費者庁が2021年に公表したポイントサイト調査資料では、利用者が確認すべき事項として、次のような項目が挙げられています。

- ポイントの獲得条件
- 付与対象外となる条件
- ポイントが付与される時期
- 推奨ブラウザやCookieなどの利用環境
- ポイントの有効期限
- ポイント交換の条件
- 運営事業者や問い合わせ方法

特に、広告主サイトへ移動した後に別サイトへアクセスした場合など、操作順によってポイント対象外になる可能性にも触れられています。[消費者庁「ポイントサイト調査結果」](https://www.caa.go.jp/policies/policy/consumer_policy/caution/internet/assets/caution_internet_210329_0001.pdf)

したがって、自動化システムは「案件を見つけたか」だけでなく、**どの条件を、いつ、どのURLで確認したか**まで保存する必要があります。

## Hiroの実行ログで分かった「主処理成功＝自動化成功」ではない理由

Hiroが運用する`auto-ai-blog`の実行ログには、自動化システムの成否を考えるうえで参考になる一次情報があります。

2026年6月27日のログでは、次の処理が記録されています。

| 時刻 | ログ上の処理 |
|---|---|
| 02:50:50 | 対象マニュアルを選択し、Codex CLIを呼び出し |
| 02:53:31 | Codex CLIによる記事生成が成功 |
| 02:53:31 | Markdownファイルをローカルへ保存 |
| 02:53:33 | GitHubへのpushが失敗 |
| 02:53:39 | 2回目のpushも失敗 |
| 02:53:45 | 3回目のpushも失敗し、処理全体がエラー終了 |

生成開始からローカル保存までは、ログの時刻差で約2分41秒でした。しかし、GitHub側にローカルへ未取得の更新があったため、3回のpushはいずれも`fetch first`で拒否されています。

これはポイ活Botの実験結果ではありません。そのため、「この仕組みで何ポイント獲得できた」と示す証拠には使えません。

一方で、次の運用原則を示す一次情報にはなります。

> 中核処理が成功しても、保存・同期・通知・照合のどこかが失敗すれば、自動化全体は成功ではない。

ポイ活へ置き換えると、次のような状態です。

- 申込みは完了したが、ポイントサイト側で「判定中」になっていない
- 付与予定ポイントは取得できたが、台帳への保存に失敗した
- 付与予定日を過ぎたが、アラートが送信されなかった
- 規約が変更されたが、古い条件のまま処理を継続した

そのため、本記事では成功条件を「申込み画面が表示された」ではなく、**記録・証拠・照合・通知まで完了したこと**として設計します。

## Pythonで作る規約順守型ポイ活システムの全体像

![規約順守型ポイ活システムの設計フロー](https://image.pollinations.ai/prompt/reward%20points%20automation%20flowchart%20terms%20check%20data%20collection%20python%20database%20alert%20KPI%20Japanese%20style?width=800&height=400&nologo=true)

基本構成は次のとおりです。

1. 公式情報、CSV、メールなどからデータを取得する
2. 規約確認済みか判定する
3. 重複利用や条件不足を検知する
4. 案件台帳へ保存する
5. 付与予定日、失効日、実付与を照合する
6. 異常だけを通知する
7. KPIを集計して継続可否を判断する

最初からブラウザ操作を作る必要はありません。初心者は、CSVとSQLiteを使った台帳から始める方が安全です。

## ステップ1：現在の作業を分解する

まず、普段のポイ活を作業単位で書き出します。

| 作業 | 初期判定 | 理由 |
|---|---|---|
| 案件を探す | 要確認 | 情報源ごとに取得条件が異なる |
| 獲得条件を読む | 人間 | 条件文の解釈が必要 |
| 還元率を比較する | 自動化候補 | 数値化できる |
| 広告を利用する | 原則として人間 | 成果発生操作に該当する |
| 利用日時を記録する | 自動化候補 | 台帳へ保存できる |
| 判定中を確認する | 要確認 | 取得方法と規約による |
| 付与予定日を監視する | 自動化候補 | 日付比較で処理できる |
| 失効日を通知する | 自動化候補 | 通知処理だけで完結する |

各作業へ次のラベルを付けます。

- `ALLOW`：規約や公式仕様で許可を確認済み
- `REVIEW`：人間による確認が必要
- `DENY`：自動化しない
- `UNKNOWN`：判断材料が不足している

`UNKNOWN`を自動実行してはいけません。安全側へ倒し、確認が終わるまで停止させます。

## ステップ2：規約・案件条件台帳を作る

最低限、次の項目を記録します。

```text
サービス名：
案件名：
規約URL：
案件URL：
確認日：
確認者：
自動アクセスの可否：
ポイント獲得条件：
対象外条件：
Cookie・推奨ブラウザ条件：
ポイント付与予定：
ポイント失効日：
問い合わせ期限：
人間が行う操作：
自動停止条件：
```

規約本文を保存する場合は、確認日時と本文ハッシュも記録します。

ただし、本文ハッシュが変わっただけで「不利な規約変更」とは断定できません。レイアウト、広告、日付表記の変更でもハッシュは変わります。

したがって、変更時の処理は次の順番にします。

1. 自動処理を一時停止する
2. 前回版との差分を保存する
3. 人間が変更箇所を確認する
4. 自動化可否を再判定する
5. 確認者と確認日を更新する

なお、`robots.txt`でクロールが許可されていても、ポイント獲得操作まで許可されたことにはなりません。利用規約、案件条件、公式APIの利用条件を別々に確認してください。

## ステップ3：「表示ポイント」ではなく期待手残りを計算する

ポイント数と円を直接足し引きするには、換金価値をそろえる必要があります。

次の式で案件を比較します。

```text
期待ポイント価値
= 付与予定ポイント
× 1ポイント当たりの換金価値
× 予想承認率

期待手残り
= 期待ポイント価値
- 追加購入費
- 月額料金
- 交換手数料
- 自動化サービス費
- 保守時間 × 時間単価
```

たとえば、次の案件を考えます。

```text
付与予定：1,000ポイント
換金価値：1ポイント＝1円
過去の承認率：80%
不要な追加購入：500円
保守時間：15分
時間単価：1,200円
```

計算結果は次のとおりです。

```text
期待ポイント価値
= 1,000円 × 0.8
= 800円

期待手残り
= 800円 - 500円 - 300円
= 0円
```

表示上は1,000ポイントでも、期待値では利益が残りません。

必要だった商品を通常価格で購入し、その結果としてポイントが付く場合は、商品代全額をコストにするのではなく、「ポイント目的で追加発生した支出」を分けて記録します。

## ステップ4：SQLiteで案件台帳を作る

CSVでも始められますが、状態管理と重複検知にはSQLiteが向いています。

### 必要な項目

```sql
CREATE TABLE IF NOT EXISTS campaigns (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    service_name TEXT NOT NULL,
    campaign_name TEXT NOT NULL,
    source_url TEXT NOT NULL,
    terms_checked_at TEXT,
    automation_decision TEXT NOT NULL,
    expected_points INTEGER NOT NULL DEFAULT 0,
    point_value_yen REAL NOT NULL DEFAULT 1.0,
    required_extra_cost_yen INTEGER NOT NULL DEFAULT 0,
    used_at TEXT,
    expected_approval_date TEXT,
    actual_points INTEGER,
    status TEXT NOT NULL DEFAULT 'candidate',
    evidence_path TEXT,
    notes TEXT,
    UNIQUE(service_name, campaign_name, used_at)
);
```

`status`は、最低でも次の状態へ分けます。

```text
candidate    候補
approved     利用を承認済み
applied      申込み・利用済み
pending      判定中
confirmed    承認済み
credited     ポイント付与済み
rejected     否認
expired      期限切れ
stopped      規約・異常により停止
```

「申込み完了」と「ポイント付与済み」を同じ成功として扱わないことが重要です。

## ステップ5：付与漏れを検知するPythonコードを書く

次は、付与予定日を過ぎてもポイントが付いていない案件を抽出する最小例です。

```python
import sqlite3
from datetime import date
from pathlib import Path

DB_PATH = Path("data/poikatsu.sqlite3")

def find_overdue_campaigns():
    today = date.today().isoformat()

    with sqlite3.connect(DB_PATH) as connection:
        connection.row_factory = sqlite3.Row

        rows = connection.execute(
            """
            SELECT
                id,
                service_name,
                campaign_name,
                expected_points,
                expected_approval_date,
                status,
                evidence_path
            FROM campaigns
            WHERE expected_approval_date IS NOT NULL
              AND expected_approval_date < ?
              AND status NOT IN ('credited', 'rejected', 'expired', 'stopped')
            ORDER BY expected_approval_date
            """,
            (today,),
        ).fetchall()

    return [dict(row) for row in rows]

if __name__ == "__main__":
    overdue = find_overdue_campaigns()

    if not overdue:
        print("期限超過案件はありません")
    else:
        for campaign in overdue:
            print(
                f"[要確認] {campaign['service_name']} / "
                f"{campaign['campaign_name']} / "
                f"予定日={campaign['expected_approval_date']} / "
                f"予定={campaign['expected_points']}pt / "
                f"証拠={campaign['evidence_path']}"
            )
```

このコードはポイントサイトへログインせず、ローカル台帳だけを確認します。最初の自動化として、規約上のリスクを抑えやすい構成です。

実行前には、次を確認してください。

```text
[ ] expected_approval_dateが正しい
[ ] statusが最新
[ ] 証拠ファイルの保存場所が存在する
[ ] 問い合わせ期限を過ぎていない
[ ] 通知先へ個人情報を送らない
```

## ステップ6：証拠を保存する

ポイントが反映されない場合、利用日時や条件を確認できる資料が必要になります。

案件ごとに、次の証拠を保存します。

- 案件名と獲得条件が分かる画面
- 対象外条件が分かる画面
- 利用日時
- 購入・申込み完了を確認できる情報
- ポイントサイト側の判定状況
- ポイント付与履歴
- 問い合わせ内容と回答

保存先の例は次のとおりです。

```text
evidence/
└── 2026-07/
    └── service-a_campaign-001/
        ├── conditions.pdf
        ├── completion-masked.png
        ├── pending-masked.png
        └── notes.md
```

ファイル名には、サービス名、案件識別子、利用日を含めます。

スクリーンショットやPDFを外部サービスへ送信する場合は、次の情報をマスクしてください。

- 氏名
- 住所
- 電話番号
- メールアドレス
- 注文番号
- ポイント残高
- Cookie
- セッショントークン
- APIキー

公開記事用の画像と、問い合わせ用の内部証拠は分離します。

## ステップ7：7日以上のシャドー運転を行う

いきなり定期実行せず、最初はシャドー運転を行います。

シャドー運転では、システムが「実行する予定だった内容」だけをログに残し、購入、申込み、広告クリックなどは実行しません。

確認項目は次のとおりです。

- 同じ案件を重複登録していないか
- ポイント数と換金価値を混同していないか
- 日付を正しく解析できているか
- 対象外条件を無視していないか
- `UNKNOWN`の案件で停止できたか
- ログ保存に失敗した場合に異常終了したか
- 通知が多すぎないか
- 個人情報がログへ出ていないか

7日間はあくまで初期確認の目安です。月次更新の案件なら、少なくとも更新を1回観測できる期間まで延長します。

合格条件の例は次のとおりです。

```text
重大な誤判定：0件
重複登録率：1%未満
日付解析成功率：99%以上
ログ保存成功率：100%
異常通知到達率：100%
規約不明案件の自動実行：0件
```

## ステップ8：人間へ戻す停止条件を固定する

次の条件では自動処理を停止します。

- CAPTCHAや本人確認が表示された
- ログイン方式が変更された
- 規約または案件条件に変更を検知した
- 獲得条件を正しく抽出できなかった
- 金額やポイント数が想定範囲を外れた
- 同一案件の利用履歴が見つかった
- Cookieや成果追跡状態を確認できなかった
- 保存先へ書き込めなかった
- 通知に失敗した
- データ取得元が公式情報か確認できなかった

停止ログには、少なくとも次の情報を残します。

```json
{
  "run_id": "20260723-060000",
  "status": "stopped",
  "step": "terms_check",
  "reason_code": "TERMS_CHANGED",
  "source_url": "https://example.com/terms",
  "last_checked_at": "2026-07-20T09:00:00+09:00",
  "stopped_at": "2026-07-23T06:00:12+09:00"
}
```

エラー文だけでなく、処理工程と理由コードを記録すると、後から集計できます。

## ステップ9：定期実行と通知を設定する

Windowsではタスクスケジューラ、Linuxではcronやsystemd timerを利用できます。

通知は、正常系と異常系を分けます。

### 即時通知するもの

- 規約変更
- データ取得失敗
- ログイン失敗
- 保存失敗
- CAPTCHAや本人確認の表示
- 付与予定日の超過
- 想定外の金額や画面変更

### 日次サマリーにまとめるもの

- 新規案件数
- 期限が近い案件数
- 付与済みポイント
- 判定中の件数
- 正常終了回数

毎回「正常終了しました」と通知すると、重要な異常が埋もれます。正常系はまとめ、異常系だけ即時に送る設計が実用的です。

また、通知処理自体が失敗することもあります。通知送信の成否をログへ残し、一定時間内にハートビートが届かなければ別経路で知らせる仕組みも検討してください。

## 専門家目線で確認したい5つのポイント

### 1. 規約はサービス単位と案件単位の両方を確認したか

ポイントサイト側で許可されていても、広告主側の条件で自動操作が認められていない場合があります。

次の4層を分けて確認します。

1. ポイントサイトの利用規約
2. ポイントサイト内コンテンツの個別ルール
3. 広告案件の獲得条件・対象外条件
4. 広告主サービスの利用規約

### 2. 成功判定を早すぎる段階に置いていないか

成功状態は一つではありません。

```text
申込み完了
→ ポイントサイトで判定中
→ 承認
→ ポイント付与
→ 交換可能
```

申込み完了時点では、ポイント獲得は確定していません。各段階を別ステータスで追跡します。

### 3. 冪等性を確保しているか

同じ処理を再実行しても、案件が二重登録されたり、通知が何度も送られたりしない設計が必要です。

重複判定には、次の組み合わせを使います。

```text
サービス名
+ 案件ID
+ 利用日
+ 注文または申込み識別子のハッシュ
```

注文番号そのものをログへ平文保存する必要はありません。照合用ハッシュへ変換する方法もあります。

### 4. 認証情報を安全に管理しているか

パスワード、Cookie、APIキーをPythonファイルやGitリポジトリへ直接書いてはいけません。

候補は次のとおりです。

- OSの資格情報管理
- アクセス権を制限した環境変数
- シークレット管理サービス
- 暗号化した設定ファイル

ログへ環境変数の全内容を出力する処理も避けてください。

### 5. フェイルクローズになっているか

判断できない場合に処理を継続する設計を「フェイルオープン」、停止する設計を「フェイルクローズ」と呼びます。

ポイント獲得に関係する処理では、次の状態をすべて停止扱いにします。

- 規約を確認できない
- 条件を抽出できない
- 通信が不安定
- ログ保存に失敗した
- 金額を確認できない
- 重複利用か判断できない

「異常時に止まること」は失敗ではなく、安全装置が正しく動いた結果です。

## よくある失敗と改善方法

### 失敗1：自動クリックから作り始める

**原因：** 成果に近い操作ほど価値があるように見えるためです。

**改善：** 台帳、ログ、期限通知、付与照合を先に作ります。ブラウザ操作は、必要性と許可を確認できた場合だけ追加します。

### 失敗2：ポイント数と利益を混同する

**原因：** 購入費、交換手数料、月額料金、保守時間を計算していません。

**改善：** 「獲得ポイント」「円換算額」「期待手残り」「実手残り」を別々に記録します。

### 失敗3：申込み完了を成功としている

**原因：** 付与まで追跡していません。

**改善：** `applied`、`pending`、`confirmed`、`credited`を分離し、付与予定日を超えた案件だけ通知します。

### 失敗4：規約変更後も処理を続ける

**原因：** 初回確認日しか保存していません。

**改善：** 規約URL、確認日、本文ハッシュ、確認者を保存し、変更検知時は自動停止します。

### 失敗5：座標クリックに依存する

**原因：** ボタン位置や画面サイズが変わると、別の場所を操作する可能性があります。

**改善：** 許可された画面操作でも、URL、要素名、金額、確認文言を検証し、一つでも不一致なら停止します。

### 失敗6：リトライだけで直そうとする

**原因：** 認証エラー、条件変更、権限不足など、再試行しても直らない障害を区別していません。

**改善：** エラーを分類します。

| エラー | 処理 |
|---|---|
| 一時的な通信失敗 | 回数と間隔を制限して再試行 |
| 認証失敗 | 即時停止して通知 |
| 規約変更 | 即時停止して人間が再確認 |
| 保存失敗 | 成功扱いにせず停止 |
| 重複疑い | 自動処理せず確認待ち |
| CAPTCHA | 回避せず停止 |

## ポイ活自動化で追うべきKPI

| KPI | 計算方法 | 判断できること |
|---|---|---|
| 実付与ポイント | 付与済みポイント合計 | 確定した成果 |
| 承認率 | 承認件数÷利用件数 | 条件誤読や追跡失敗 |
| 追跡率 | 台帳へ記録できた利用件数÷全利用件数 | 記録漏れ |
| 期待手残り | 期待ポイント価値－追加費用－運用費 | 利用前の採算性 |
| 実手残り | 実付与の円換算額－追加費用－運用費 | 実際の採算性 |
| 自動処理成功率 | 全工程正常終了回数÷総実行回数 | システムの安定性 |
| 付与漏れ検知数 | 付与予定日超過を検知した件数 | 回収漏れの防止効果 |
| 誤検知率 | 誤った警告数÷全警告数 | 通知品質 |
| 人間介在時間 | 月間の確認・修正時間 | 自動化効果 |
| 保守1時間当たり手残り | 月間実手残り÷保守時間 | 継続価値 |
| 規約停止件数 | 規約不明・変更で停止した件数 | 安全装置の作動状況 |
| 証拠保存率 | 証拠がそろった利用件数÷全利用件数 | 問い合わせ可能性 |

最初に目指すべきなのは、ポイント数の最大化ではありません。

```text
追跡率：95%以上
証拠保存率：100%
異常通知到達率：100%
重大な誤操作：0件
規約不明案件の自動実行：0件
```

この基盤が整ってから、期待手残りや人間介在時間を改善します。

## 「そこまで管理すると割に合わない」という反論について

この反論は正しい場合があります。

ポイ活の利益幅が小さいと、次のコストが獲得額を上回ります。

- Python開発時間
- VPSやデータベースの利用料
- 通知サービス料金
- 画面変更への対応
- 規約確認時間
- セキュリティ管理
- 誤検知の確認時間

月間手残りが1,000円なのに、毎月2時間の保守が必要なら、金銭目的の仕組みとしては効率的とはいえません。

その場合は、次のどれかを選びます。

1. 期限通知と付与漏れ検知だけ残す
2. 有料インフラを使わずローカル実行へ戻す
3. 保守時間が大きい情報源を廃止する
4. Python学習用プロジェクトと割り切る
5. 自動化自体を停止する

「止める」という判断もKPI改善の一部です。

## Web自動化が向かないケース

次の目的には利用しないでください。

- ゲームやアンケートを人間の代わりに実行する
- 広告を機械的に閲覧・クリックする
- 複数アカウントで紹介報酬を得る
- CAPTCHAやアクセス制限を回避する
- 虚偽情報で案件へ申し込む
- 短期解約を前提に不要な契約を繰り返す
- 本人以外の情報やアカウントを利用する
- 広告主が想定していない方法で成果を発生させる

技術的に実行できることと、規約上許可されていることは別です。

## まとめ：ポイ活の完全自動化ではなく、管理の無人化を目指す

ポイ活とWeb自動化を安全に組み合わせるなら、広告クリックやゲーム操作の代行から始めるべきではありません。

先に自動化するのは、次の作業です。

- 案件条件の記録
- 還元率と期待手残りの比較
- 重複利用の検知
- 証拠の整理
- 付与予定日の監視
- ポイント失効前の通知
- 実付与との照合
- KPIと保守時間の集計

Hiroの`auto-ai-blog`実行ログでも、記事生成とローカル保存が成功した後に、GitHubへのpushが3回失敗しています。この一次情報が示すのは、主処理だけを見て「完全自動化できた」と判断してはいけないということです。

ポイ活でも同じです。申込み、判定、承認、付与、記録、通知まで追跡できて初めて、一つの運用ラインになります。

完全無人化を目標にするのではなく、**正常時の管理作業を減らし、規約・金額・認証・追跡に異常があれば確実に止まる仕組み**を目指してください。
